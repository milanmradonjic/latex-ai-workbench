# Version 4.7.0 verification

This records the release that adds `make snapshot` and `make snapshots` (step 3.6 of [the plan after 4.4.0](plan-after-4.4.0.md)): a copy of every file of the project, kept outside it, in two rotating tiers.
It touches the owner's machine outside the project, so the design was put to the owner first and accepted on 14 October 2026 (the plan records the decisions).
Tested on 2026-10-14 on Linux (x86_64, GNU Make 4.3, Git 2.43.0, Python 3.13.16, 3.12.13 and 3.11.17) with TeX Live 2023 from Debian: `latexmk`, `chktex`, `bibtex`, `lualatex`, `xelatex` and `biber`.

## Found on the way

- **A rotation rule that the scope did not need to state.** The scope says a repository whose `PERIOD` differs from the current period is deleted. With two repositories that is not enough: a snapshot after a gap of three weeks goes to the other slot and the old repository, now far past its two weeks, stays on disk. The rule is "older than the previous period", for both slots, which is also what keeps a repository from the future (a clock that went backwards) from being deleted.
- **What Git does with a path of its own.** `update-index` ignores a path with a `.git` component (a submodule's `.git` file, a nested repository) and prints "Ignoring path" with exit status 0, so no filter is needed and none is written; a test pins that a nested repository's files are kept and its `.git` is not.
- **A snapshot has to say what it did not do.** An unreadable folder stops it, an unreadable file makes Git say which one, and a file over the limit is named in the output, so that "I have a copy" is never true of a file that was left out without a word.
- **Refusals before writes.** Both tiers are opened, and old repositories deleted, before the first commit is made, so a refusal in one cannot leave the other with a snapshot that the message did not mention.
- **The first step of updating and migrating cannot assume the new Makefile.** A project from 4.6 and before has no `make snapshot`, so the guides give the form that runs from the new release's folder (`runtime.py snapshot --project PROJECT`), and the output says "the snapshots action of the runtime" instead of naming a Make target the project lacks.

## Not verified

- **Hosted runs of this pull request**, with TeX Live 2026 in the `validate` job.
- **Two snapshots at the same time.** Git's own index lock makes the second fail with Git's message; the deletion of an old repository is not locked, so a second snapshot that opens a repository while the first deletes it fails with an error and writes nothing.
- **macOS and Windows.** `Path.home()`, a path with a space, a case-insensitive file system (where `.GIT` and `.git` are one folder) and Windows' file names were not exercised. Git 2.43 only: the commands used (`read-tree --empty`, `update-index -z --stdin`, `write-tree`, `commit-tree`, `update-ref`, `init --bare --template=`) are all old, but no other version was run.
- **A system-wide Git configuration.** `GIT_CONFIG_NOSYSTEM=1` is Git's own switch; no test can write `/etc/gitconfig`.
- **Disk use over time.** Snapshots are loose objects and nothing runs `git gc`; a repository is deleted when it is two periods old, which bounds it, but a project with large changing files will use space in proportion.
- **Agents.** The policy and the skill file do not yet tell an agent to take a snapshot before a risky change; that belongs to step 3.7, which rewrites the skill's update recipe, and to the owner's gate on the agent rules.
