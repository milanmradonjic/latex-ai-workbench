# Version 4.8.0 verification

This records the release that replaces the two rotating tiers of [4.7.0](verification-4.7.0.md) by three snapshot stores with counted retention: `manual` (what `make snapshot` takes; the workbench never deletes from it),
`weekly` (the first snapshot of each calendar week, the newest 6 kept) and `frequent` (when files changed, the newest 60 kept). It was asked for by the owner the day 4.7.0 was merged, after the question what a clock that
jumps forward would do to the history of 4.7.0 (it deleted all of it); the design is the owner's, and the plan records it.
Tested on 2026-10-14 on Linux (x86_64, GNU Make 4.3, Git 2.43.0, Python 3.13.16, 3.12.13 and 3.11.17) with TeX Live 2023 from Debian.
The hosted results are at the end of this record (added by the record of 4.9.0).

## Found on the way

- **What the design asks of Git.** A snapshot is a commit of its own with no parent, so the oldest can go without rewriting the others. Dropping it is `update-ref -d` and `prune --expire=now`; an experiment before any code showed 20 objects become 12 after two of five snapshots are dropped, `fsck` clean, and the dropped snapshots' unique files gone while the others' remain. Stores are never repacked, so every file is loose and `prune` reaches it.
- **The workbench no longer deletes a folder.** 4.7.0 had one `rmtree`, guarded by five refusals; the folder rotation is gone, and what is deleted is a reference and the files only it held, inside a repository the workbench made.
- **The clock now decides one thing:** whether this calendar week already has its weekly snapshot, by the computer's own time zone. A jump forward or back gives one snapshot too many or too few; the tests put it at the year 2032 and back and nothing is deleted. The tests fix the time zone to UTC, so that the week boundary is the same on every machine.
- **The launchd files use absolute paths and no `WorkingDirectory`**, on the review's point that a folder launchd cannot enter fails before the program starts and leaves no log, while a program that starts and cannot read a folder reports it.
- **The old tests of the rotation went with it,** and what 4.7.0 established (contents, exact bytes, isolation, refusals, hardening, the commands) stayed in `test_scope_4_7_0.py` with its helpers adapted. The new file imports those helpers; the step that regroups the tests by component can fold them together.
- **A list of stores in three places** (`TIERS`, `KEEP`, `meaning()`), noted by the review as the one place the module is not as lean as it could be; it is three short lines, and merging them would hide which store has no limit.

## Not verified

- **launchd.** The two agents were written where launchd cannot be run. They are valid property lists and the command each runs works and fills the right store; what launchd does with them on a Mac (a start missed in sleep, one missed while switched off, `RunAtLoad`, the privacy protection of `~/Documents` and similar folders, log append) is from its documentation as remembered, and untested. The owner's first run is the test.
- **An older Git.** Only 2.43.0 was run. `commit-tree -m` needs 1.7.9, `core.hooksPath` 2.9 (harmless on older Git: the repository has no hooks), and `%(committerdate:raw)`, `update-ref` with an empty old value and `init --template=` were not run on another version.
- **macOS and Windows,** and a network file system for the lock.
- **Restoring from the oldest snapshot while a timer drops it** could give a partial checkout (a suspicion; only the oldest of a full store is at risk, and only for the moment of the drop).
- **A user's `git gc` on a store:** the files are packed and later drops no longer free their space; it is a leak of space only, and the docs say the stores need no `gc`.
- **A flapping clock** (above), and **disk use:** the frequent store holds up to 60 snapshots of a project in one repository, so only changed files add to it; a first snapshot of a 20,000-file, 223 MB project took 10 s in the review and a poll with nothing changed 1.7 s.
